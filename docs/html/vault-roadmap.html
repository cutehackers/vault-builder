Vault 개선 로드맵

OpenWiki 조사로 만든 개선 계획(B1~B6)과 앞서 검토한 개선안(A1~A5)을 합쳐 제안 13개로 정리했습니다. 결정 4개는 2026-10-28에 모두 정했습니다. 그 뒤 vault 연결 규칙을 다시 검토해서 효율안1~3과 MCP 설치 점검 결과 발견1~6을 제안11~13에 반영했습니다. 제안11~13은 2026-10-29에 구현을 마치고 main에 병합했습니다(a843778). 테스트 582개와 release gate를 통과했고, 리뷰 판정은 Ready to merge(수용 근거 28/28)입니다. 이 Mac에도 새로 설치했고, 수동 점검 세 가지(서버 하나만 연결, doctor 통과, uninstall 뒤 남는 것 없음과 재설치 왕복)를 모두 통과했습니다. 코드 참조는 2026-10-28 기준 현재 checkout에서 확인했습니다.

A1~A5 앞 검토의 개선1~5 B1~B6 OpenWiki 계획의 개선1~6 OpenWiki 자체의 동작은 다시 확인하지 않고 조사 결과를 그대로 썼습니다

핵심 진단

약점1

원본이 바뀌어도 모릅니다

drift 검사는 raw/ 사본의 해시만 비교합니다. Stale sources 값은 raw drift와 누락만 셉니다(tools/wiki/lib/metrics.py:69). 그래서 원본 repo가 바뀌어도 이 값은 0이고, 0이라는 값이 건강하다는 증거가 되지 못합니다.

약점2

근거 단위가 파일 전체입니다

evidence는 path#sha256=... 형태만 읽습니다(tools/wiki/lib/lint.py:763). 큰 소스에서 한 줄만 바뀌어도 그 파일을 가리키는 claim이 모두 무효가 되고, 어느 claim이 실제로 틀렸는지 구분할 수 없습니다.

계획 정정

OpenWiki 계획의 사실 몇 가지가 현재 코드와 다릅니다. 아래 제안은 정정한 사실을 기준으로 씁니다.

  • 정정1
    vault-graph 구현 repo가 이 머신에 없다$HOME/workspace/vault-graph에 있습니다. spec이 다른 사용자의 홈 경로를 가리켜서 못 찾은 것입니다. commit 148개, MCP 읽기 도구 9개(search_vault, ask_vault, build_context_pack, find_related, get_decision_trace 등)가 구현되어 있습니다. 그래서 계획의 결정2는 이미 답이 나왔습니다.
  • 정정2
    workspace registry를 새로 만든다연결 설정은 이미 두 개 있습니다. vault-builder install이 쓰는 vault-map.json이 하나이고, vault-graph의 VaultCatalog가 또 하나입니다. VaultCatalog에는 이미 active_vault_id와 여러 vault 범위 검색이 있습니다(src/vault_graph/operation/scope/vault_catalog.py). 새로 만들면 세 번째 설정이 생깁니다.
  • 정정3
    OpenWiki의 설치 영수증 방식을 참고한다이미 구현되어 있습니다. install은 vault 밖에 쓴 파일을 hash와 함께 manifest v2에 기록하고, uninstall과 doctor가 이 기록을 씁니다. 그래서 로드맵에서 뺐습니다.
  • 정정4
    lint.py:460, lint.py:728, index.md 16.7KB현재 builder 기준으로 canonical_source를 raw/ 아래로 제한하는 규칙은 lint.py:508, evidence 해석은 lint.py:763에 있습니다. wiki/index.md는 지금 19.5KB입니다.

제안11

MCP 서버를 하나로 줄이고 설치와 제거를 깔끔하게 만든다

✓ 구현 완료

install을 점검해서 MCP 등록 문제 6개를 찾았습니다.

  • 발견1 같은 서버를 .mcp.json과 ~/.claude.json 두 곳에 무조건 등록합니다(installing.py:528, :570).
  • 발견2 doctor가 지워진 .mcp.json을 다시 만듭니다(uninstalling.py:642-680).
  • 발견3 doctor가 user scope 항목의 interpreter를 검사하지 않습니다(uninstalling.py:591-604).
  • 발견4 interpreter 경로가 python@3.12처럼 특정 버전에 고정됩니다.
  • 발견5 쓰기 도구가 모든 저장소 세션에 노출됩니다.
  • 발견6 ~/.claude.json 전체를 다시 쓰므로 실행 중인 앱과 쓰기가 겹칠 수 있습니다.

바꾸는 방향(효율안1)은 다음과 같습니다.

  • 사용자 단위 MCP 서버 하나를 user scope에 한 번만 등록합니다. 이 서버는 vault-map.json을 읽고 요청마다 대상 vault의 tools/wiki/cli.py를 실행합니다. 그래서 각 vault의 검사는 그 vault의 도구 버전이 그대로 맡습니다.
  • .mcp.json은 만들지 않고, doctor도 다시 만들지 않습니다. vault가 늘어나도 서버는 하나입니다.
  • 서버는 상태를 두지 않습니다. 호출마다 vault-map.json을 다시 읽고 대상 vault의 CLI를 새 프로세스로 실행합니다.
  • 읽기와 검색은 OpenWiki처럼 이 세션이 닿는 vault(세션 vault, 또는 저장소에 연결된 vault)만 대상으로 하고, 결과마다 vault 이름을 붙입니다.
  • 쓰기는 OpenWiki처럼 모든 세션에 보입니다. vault 인자를 반드시 받고, team vault를 포함해 어떤 vault에도 쓸 수 있으며, publish-draft 검증이 막습니다. 경로 인자는 고른 vault 안의 상대 경로만 받습니다.
  • uninstall한 vault는 install 하나로 다시 설치됩니다(결정42, 결정44).
  • doctor는 등록된 명령으로 서버를 실제로 띄워 MCP 시작 요청과 도구 목록 요청에 응답하는지 확인합니다.
  • uninstall은 마지막 vault를 제거할 때 서버 등록과 공용 파일을 모두 지웁니다. 다른 vault가 남아 있으면 그 vault에 관한 기록만 지웁니다.

    stale claim이 하나만 있어도 페이지 전체에 모델 작업이 걸리고, 대형 repo에서는 토큰 사용량이 크게 늘었다는 사례(#934)가 있습니다. vault는 점검만 자동으로 하고, 갱신은 사람이 승인합니다(제안3, 제안8).

  • 위험2

    검증 범위

    OpenWiki는 소스 구간이 바뀌었는지만 추적하고 페이지 내용이 맞는지는 검증하지 않습니다. vault의 모순 처리와 human-lock은 그대로 유지합니다.

  • 위험3

    의존성

    OpenWiki는 LangChain DeepAgents에 의존하고 텔레메트리가 기본으로 켜져 있습니다. 코드는 가져오지 않고 설계만 참고합니다.

결정이 필요한 항목

  • 결정1

    코드 repo를 claim 근거로 직접 가리킬 것인가

    등록된 repo를 읽기 전용 외부 권위로 인정할지, 아니면 repo 사본을 raw/에 주기적으로 저장할지 정해야 합니다.

    결정됨(2026-10-28): 직접 가리키기. 사본을 저장하면 저장 직후부터 낡기 때문에 약점1이 그대로 남습니다. 제안4는 repo:// 증거를 받는 범위로 진행합니다.

  • 결정2

    vault 연결 설정은 어느 쪽을 기준으로 할 것인가

    builder의 vault-map.json과 vault-graph의 VaultCatalog 중 하나를 기준으로 정해야 합니다.

    결정됨(2026-10-28): vault-map.json을 기준으로 하고 workspace를 여기에 더합니다. AGENTS.md 규칙9에 따라 계약은 vault-builder가 관리하고, install과 uninstall이 이미 이 파일을 manifest에 기록합니다. vault-graph는 이 파일을 읽기만 합니다.

  • 결정3

    공통 규칙을 어느 요약까지 보여줄 것인가

    personal 역할 vault의 공통 규칙만 보여줄지, team vault의 공통 규칙도 보여줄지 정해야 합니다.

    결정됨(2026-10-28): 요약에 넣지 않습니다. OpenWiki도 모든 repo에 적용되는 공통 규칙 개념이 없고, 위키 내용을 미리 주입하지 않고 필요할 때 검색합니다. 공통 규칙은 project 없이 personal vault에 두고 검색으로 찾습니다. 검색하지 않으면 규칙을 놓칠 수 있다는 점은 감수합니다.

  • 결정4

    MCP 읽기 진입점과 중복 등록을 어떻게 정리할 것인가

    vault-graph를 읽기 진입점으로 삼을지, 그리고 user scope 항목이 있을 때 .mcp.json을 만들지 않도록 결정7을 바꿀지 정해야 합니다.

    결정됨(2026-10-28): 중복 등록을 지금 고치고, user scope 등록을 남깁니다. 원인은 같은 서버를 두 곳에서 따로 등록하기 때문입니다. vault의 .mcp.json은 결정7에 따라 vault 안 세션용 llm-wiki를 등록하고, ~/.claude.json은 결정20에 따라 모든 세션용 llm-wiki-personal을 등록합니다. 이후 검토에서 방향을 넓혔습니다. 서버를 하나로 만들어 user scope에 한 번만 등록하고, .mcp.json은 만들지 않습니다(제안11, 효율안1).

남은 처리: vault에 commit되지 않은 scratch/reports/2026-10-28-lint.md가 남아 있습니다. 제안1을 적용하면 이런 파일은 더 생기지 않지만, 지금 있는 파일을 commit할지 지울지는 따로 정해야 합니다.
